# Operational Surface and Component Tiers

This document is the running inventory of every platform component that the template operates. It sorts them into three tiers. It also holds the budget rule for adding to the always-on floor. [`adoption-path.md`](adoption-path.md) runs the other way: it governs *removing* from the floor. This document makes principle 2 of [ADR-0000](adr/0000-platform-foundations.md), the *thinnest viable platform*, checkable and not only a goal.

[ADR-0000](adr/0000-platform-foundations.md) sets the platform-engineering budget. Under that budget, the raw component count is not the unit that matters. Most of these components are the real production floor for a multi-tenant application at meaningful load. The unit that matters is the **operational surface that the platform team must understand at 3am**. The tiers make that surface explicit and bounded.

## The three tiers

### Core: always on

This is the real floor. Every environment runs these components. A project removes one only in one of two ways:

- It writes an ADR that shows the floor already covers the concern of the component.
- It takes a row from [`adoption-path.md`](adoption-path.md) and records the restore trigger that it watches.

The table has three columns about operations:

| Column | Meaning | How to read it |
| --- | --- | --- |
| **What stops working** | The blast radius: the path the component sits on, and what still serves when it is down. The path is deploy, request, diagnosis, or data | Read down it during an incident. Read across it to decide whether a row can be deferred |
| **Recurring obligation** | The work that arrives whether or not anything is wrong | This is the work that a busy quarter defers with no warning |
| **Failure needs** | What the responder must already have or know when the component is the cause of a failure at 3am | Read it before the incident, not during it |

Together, the columns are the demand side of the capacity question in [ADR-0000](adr/0000-platform-foundations.md). This document states no headcount for them. A project sums this column against its own coverage obligations and reaches its own number.

**Four of these rows exist because axis B is at maximum**: the forge, the registry, outbound mail, and alert routing. Each one is a first-class decision here, not a signup. On other platforms they are accounts.

**Outbound mail is the hardest of the four.** Its main cost is deliverability reputation, and engineering effort cannot remove that cost. It is the **only** platform component where this is true. So [`adoption-path.md`](adoption-path.md) ranks it first to give up on a move down axis B. It is rank 1 in the managed-swap band of that document. It is also the heaviest recurring row in this document. So the platform ships, as its default, the component that it advises almost every adopter to hand over first. This is not a contradiction. It is the correct reading of axis B at maximum:

- The position on axis B makes self-hosting mail the default.
- The ranking makes giving up mail the cheapest way back down.

### Scale: a documented swap when a real signal needs it

These components do not ship by default. Each one is a variant that the Core floor grows into when a measured signal appears. **A Scale row is legitimate only if its seam already exists.** Without a seam, the row is a bet, not a deferral, per [ADR-0000](adr/0000-platform-foundations.md).

**The seam marker describes the forward direction only.** A swap that is cheap to adopt is not always cheap to leave. So this table records the two costs separately. For the same reason, [`adoption-path.md`](adoption-path.md) ranks reductions by the cost to reverse, not by the saving. When the reversal of a row is a data move, the row is one-way once data exists. Adopt it when the trigger fires, not before.

| Swap | From Core | Trigger to adopt | Forward seam | Cost to reverse |
| --- | --- | --- | --- | --- |
| **Mimir** | Prometheus | metrics need multi-tenant isolation, HA, or durable long retention in object storage | ✅ It is Prometheus-compatible: the same query API, dashboards, and alert rules. So the swap touches storage config, not instrumentation, per [ADR-0500](adr/0500-observability.md) | **moderate, and asymmetric.** Dashboards and rules return unchanged. But history written to the bucket does not come back into a local TSDB. So either Mimir stays for reads, or the retention obligation that justified it is dropped first |
| **Temporal for a given trivial job** | outbox with a small worker | a best-effort job gets a second step, a cross-service call, compensation, or a durability guarantee | ✅ Temporal is already Core. This seam decides only whether one job earns a workflow, per [ADR-0302](adr/0302-temporal.md) | **low**, and limited to one job. Reversal is rare, because the trigger is an added step, and teams seldom remove steps |
| **Temporal Worker Controller** | unversioned workers, a wall-clock budget, and `workflow.GetVersion` on divergent changes | the wall-clock time of a workflow is legitimately longer than a deploy cycle, or a non-determinism failure reaches production twice | ✅ The worker shape is a chart value. Adopting it renders `WorkerDeployment` CRs and installs the controller. Workflow code does not change, because Pinned executions need no patching, per [ADR-0302](adr/0302-temporal.md) | **moderate.** Removing the controller is a values change. But a `WorkerDeployment` **blocks on a finalizer** while pollers remain. So the CR stays `Terminating`, and Argo cannot create it again. To reverse, first scale the versioned Deployments to zero and wait for the pollers to expire |
| **Collector gateway tier** | DaemonSet only | the trace volume justifies tail sampling | ✅ Services always emit to `localhost:4317`. So the gateway is a deploy, not a code change, per [ADR-0500](adr/0500-observability.md) | **low.** Remove the deploy, and sampling policy returns to the DaemonSet. It is truly symmetric, because the services never knew that the gateway existed |
| **Loki and Tempo microservices mode** | monolithic single binary | the ingest volume of one backend is too large for a single Deployment | ✅ Object storage already holds the data. So the split is a values change, not a data migration | **low.** Object storage holds the data in both shapes. So the way back is the same values change in reverse. This is the most reversible row here |
| **k6-operator** | the k6 binary on a developer or CI machine | k6 reports `dropped_iterations` above 0 at the target rate, or the team needs absolute capacity figures and not relative regression signals | ✅ Scenarios do not change. Only the place where the VUs run changes, per [ADR-0601](adr/0601-testing-strategy.md) | **low.** The scenarios are the artefact, and they do not change. Only the runner does |
| **ClickHouse** | the analytics service on the shared Postgres | funnel-query p95 above 2s against the declared rollup window, or the events table keeps more than about 10M rows each month | ✅ Collection, the routing connector, and the panel do not change. Only the store and queries of the service move, per [ADR-0700](adr/0700-analytics.md) | **high: one-way once the data exists.** The queries were rewritten for a column store. The volume that triggered the move is the volume that Postgres could not hold. So reversal is a data move back into the store that could not hold it |
| **Dependency-Track** | Trivy as a merge gate, and the SBOMs already attached as OCI referrers | a compliance obligation that needs provable continuous vulnerability management, or CVE triage across the fleet that becomes monthly, not annual | ✅ SBOMs are already produced, signed, and stored, and it backfills from them. So adopting it costs the components, not the data, per [ADR-0104](adr/0104-supply-chain-security.md) | **low.** Drop the chart and its Postgres tenancy. The SBOMs stay in the registry, where the evidence lives. The accumulated triage state is lost |
| **Longhorn** | `local-path` volumes | a Postgres restore rehearsal takes more than half the RTO | ⚠️ This is a **bet**. Existing volumes migrate one workload at a time. So this is a data move, not a values change, per [ADR-0200](adr/0200-cluster-topology.md) | **high, in both directions.** Each direction is a data move for each workload. It is the only row here that is expensive to adopt *and* expensive to leave. So it is marked a bet, not a deferral |
| **GlitchTip** | `exception.*` records grouped by fingerprint in Loki and Grafana | fingerprint triage becomes routine work and not incident work, or the novelty window misses a fault that reached a customer | ✅ It ingests the Sentry envelope protocol. So the collector gets an exporter, and services need no new instrumentation, per [ADR-0503](adr/0503-error-tracking.md) | **low**, except for history. Drop the exporter and the chart, and grouping returns to Loki. But the accumulated fingerprint history leaves with the component, per [ADR-0503](adr/0503-error-tracking.md) |

**Dependency-Track is the row that the budget rule keeps out of Core.** It answers a question that nothing on the floor answers: does a CVE published today affect an image built in March. To answer it, it costs a JVM heap of several gigabytes, a Postgres tenancy, and a mirrored vulnerability database. Trivy at the merge gate is push-shaped and catches what the build produces. Dependency-Track is the pull-shaped half. The gap is real. The platform accepts it until one of its triggers fires, per [`reference/risk-register.md`](reference/risk-register.md).

## Budget rule

The floor has a cost. Every Core component is a system that the platform team must be able to reason about during an incident. So:

- **Nothing joins Core without an answer to one question: does the floor already cover this.** A new always-on component must show that no existing Core part serves its concern. If an existing part covers 90% of the need, that is the answer.
- **Prefer the Core floor over a Scale variant until a measured signal appears.** To pick the scale-tier variant of a component before the scale exists is the typical over-commitment of this template. Ship the floor, and document the seam.
- **A Scale swap needs a written trigger**, not a preference. The trigger is a measurable condition, such as ingest volume, tenant count, or retention window. The table above and the owning ADR state it.
- **An Opt-in component ships off.** It adds no operational surface until a project turns its flag on. From then on, that project owns its runbook.

This budget makes principle 3 of [ADR-0000](adr/0000-platform-foundations.md), *operational sovereignty*, affordable. That principle is a **hard constraint**. The platform does not give up self-hosting to win back operational budget. So the floor is the only lever left. When the work to operate the floor keeps pushing out feature work, the response is one of these:

- *Remove or consolidate* a Core component, per [`adoption-path.md`](adoption-path.md).
- Add capacity.

The response is never to keep adding.

A project with a weaker sovereignty requirement sits at a different point on axis B. It says so in its own ADR, per *Moving down axis B* in [ADR-0000](adr/0000-platform-foundations.md). That is a different position. It is not an escape hatch inside this position.
