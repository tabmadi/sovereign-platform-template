# ADR-0300: Data and Migrations

- **Status:** Accepted
- **Date:** 2026-08-06
- **Deciders:** Platform team
- **Related:** [ADR-0000](0000-platform-foundations.md), [ADR-0100](0100-language-and-runtime.md), [ADR-0200](0200-cluster-topology.md), [ADR-0201](0201-gitops.md), [ADR-0202](0202-secrets.md), [ADR-0301](0301-data-lifecycle-privacy.md), [ADR-0302](0302-temporal.md), [ADR-0303](0303-api-contracts-and-lifecycle.md), [ADR-0304](0304-identity-and-authorization.md)
- **Decides:** One Postgres cluster holds one logical database per service, with sqlc queries and dbmate migrations, and no service reaches another's data.

## Context

Every backend service needs persistent state. This ADR decides the engine, its operation, schema evolution, service access, and parity in one place.

Several platform components already require Postgres: Kratos and Hydra, OpenFGA, and Temporal. A second engine for application services means two engines to operate.

Authz-relevant mutations are workflows, per [ADR-0302](0302-temporal.md). So the database needs no built-in outbox.

## Decision drivers

1. **One engine.** Polyglot persistence is a permanent operational cost, and the service count multiplies it, per [ADR-0000](0000-platform-foundations.md).
2. **Service-owned data.** A service's data is private. Other services read it only through that service's HTTP API, per principle 10 of [ADR-0000](0000-platform-foundations.md).
3. **A schema change is reviewed as a diff**, in the same pull request as the code that depends on it.
4. **Parity.** Whatever produces a working database in production works locally with one command, from the same artefact.
5. **No extension becomes knowledge that only some people have.** An extension is a per-service decision, recorded in the service README.
6. **A tenant cannot read another tenant's rows, even when application code is wrong.**

## Considered options

### Engine

The store holds customer data. So it is the most expensive exit on the platform, per principle 4 of [ADR-0000](0000-platform-foundations.md), and it is compared at full depth.

| Option | Already required by the platform | Distributed by default | What it costs at this shape | Verdict |
| --- | --- | --- | --- | --- |
| **PostgreSQL** | **yes**: Kratos, Hydra, OpenFGA, Temporal | no. A read replica is the growth path | nothing beyond the cluster that the platform components already need | **Chosen.** It has strong consistency, transactional DDL, and mature replication and backup tooling. Its extensions cover the expected needs. It has the best Go driver, with first-class sqlc support *(documented)* |
| MySQL or MariaDB | no | no | a second engine to operate beside the one the platform components already need *(reasoned)* | It adds an engine and no capability. It is behind on `NUMERIC` and transactional DDL, but neither is why it loses |
| CockroachDB | no | yes, and that is its purpose | multi-node consensus on every write. Its PostgreSQL wire-protocol compatibility is close, not equal *(documented)* | It solves horizontal write scaling and multi-region residency. Neither is a requirement here. The platform components above are tested against PostgreSQL, not against a compatible dialect |
| YugabyteDB | no | yes | the same as CockroachDB, with a real PostgreSQL query layer on a distributed storage engine | The strongest distributed option on compatibility, with the same result. It buys a capability that this axis position does not need, and every write pays for it |
| SQLite | no | no | none: it is a file | Correct at axis A low. At axis A high, several deployables share the store, and that is the one thing it cannot do |
| A document store beside Postgres | no | varies | polyglot persistence pays an operational cost per engine | Rejected on principle 5. `jsonb` covers the document shapes this platform has |

### Cluster operator

| Option | Kubernetes-native CRDs | Pooler included | Verdict |
| --- | --- | --- | --- |
| **[CloudNativePG](https://cloudnative-pg.io/documentation/current/)** | `Cluster`, `Pooler`, `Backup`, `ScheduledBackup` | **yes**, as a CRD | **Chosen.** A single-binary operator. It gives HA through streaming replication, and failover and switchover as CRD operations. It writes backups to object storage, with PITR through Barman. It is Apache-2.0 and a CNCF Sandbox project. That is the least mature governance signal of the four, and principle 4 records it openly. The exit is a `pg_dump` and a different operator, because the data is plain Postgres *(documented)* |
| Zalando postgres-operator | yes | separate | Mature, with a larger configuration surface for the same capability |
| Crunchy PGO | yes | separate | Capable, with a heavier component set |
| Percona Operator for PostgreSQL | yes | **yes** | A [hard fork of Crunchy PGO](https://www.percona.com/blog/percona-operator-for-postgresql-3-0-0-hard-fork-olm-scoping-major-upgrades/). It carries Percona's Postgres distribution and its own monitoring stack, which is a second stack beside the one in [ADR-0500](0500-observability.md) |
| StackGres | yes | yes | The broadest feature set and the largest operational surface of the four |
| Raw Patroni | **no**: not Kubernetes-native | no | Every CRD operation above becomes a runbook |

### SQL access

| Option | Query plans visible | Runtime cost | Verdict |
| --- | --- | --- | --- |
| **sqlc and pgx** | **yes: the SQL is hand-written** | none. The Go is generated | **Chosen** *(reasoned)* |
| GORM, ent, bun | hidden behind an abstraction | reflection or builder overhead | Hidden query plans become a liability at the point where load makes them matter |
| sqlx | **yes: the SQL is hand-written** | reflection, per row scanned | The same authored SQL as the chosen option. It checks the result shape at runtime, not at compile time. sqlc reads the schema and generates the struct instead |
| `database/sql` by hand | yes | none | sqlc produces the same thing with types, at no cost |

### Migrations

| Option | Schema is authored as | Runs as | Added toolchain | Verdict |
| --- | --- | --- | --- | --- |
| **dbmate** | plain SQL, one file per change, with `up` and `down` sections | one static binary | none: a Go binary, the same one locally and in the init container | **Chosen.** It meets driver 3 in its most literal form: the review artefact is the SQL that runs *(reasoned)* |
| golang-migrate | plain SQL, two files per change | a binary or a Go library | none | Equal in every way that matters here. It splits each change across two files, not one |
| goose | SQL or Go migrations | a binary or a library | none | Go migrations are its difference. Here a backfill is a Temporal workflow, not a migration |
| Atlas | a **declarative desired-state** schema, with the migration computed | a binary, and a plan step | none, but [parts of the workflow are a paid tier](https://atlasgo.io/pricing) | The strongest alternative and the closest call. A declarative schema is a better review artefact than a diff of DDL. It is rejected because the generated plan runs, not the authored file. So the reviewed object and the executed object are different |
| Flyway or Liquibase | SQL, or XML or YAML changelogs | a JVM | **a JVM in the init container** | [ADR-0100](0100-language-and-runtime.md) bars the runtime. The changelog formats are a second schema language |
| Hand-run `psql` scripts, the honest baseline | plain SQL | whoever runs it | none | Nothing records which scripts an environment has applied |

### Multi-tenancy

| Option | Isolation when application code is wrong | Migration matrix | Cost per tenant | Verdict |
| --- | --- | --- | --- | --- |
| **`org_id` column plus Row-Level Security** | **the database refuses the row** | one schema | a row | **Chosen.** Driver 6 needs a guarantee below the application. RLS is the only option that puts one there without multiplying the schema *(reasoned)* |
| `org_id` column, filtered in application code only | none: a missing `WHERE` returns every tenant | one schema | a row | The failure is silent. It is the most common multi-tenant data breach |
| Schema per tenant | strong, by search path | **one migration run per tenant** | a schema, plus catalogue bloat past a few thousand | The matrix grows out of control. Every migration becomes an N-way partial-failure problem |
| Database per tenant | strongest | one run per database | a database and a connection pool | A regulated tenant needs this isolation, at a cost that only that tenant justifies. Such a tenant gets its own service and cluster instead |

## Decision

### Topology: one logical database per service, one shared cluster

| Rule | Consequence |
| --- | --- |
| Service A cannot connect to service B's database | Credentials are per service |
| No cross-database queries | Cross-service data goes over HTTP, per [ADR-0303](0303-api-contracts-and-lifecycle.md) |
| One shared physical cluster | Operational cost grows with clusters, not with services. Read replicas arrive when the load of one service justifies them |
| Compliance isolation gets its own cluster | Never its own schema in the shared cluster |

### Connection pooling: PgBouncer in transaction mode

CNPG's `Pooler` CRD deploys it between every service and the cluster.

| Option | How it is deployed here | Picked over it because |
| --- | --- | --- |
| **PgBouncer** | a CNPG `Pooler` CRD. The operator already owns its lifecycle | the chosen operator renders the pooler as a resource. So it costs a values block, not a component *(reasoned)* |
| pgcat | its own chart | It adds sharding and load balancing that this topology does not have, and it leaves the CRD path |
| Odyssey | its own chart | Stronger multi-threaded throughput, but in a component the operator does not manage |
| Application-side pooling only | nothing | `pgx` already pools per replica. It cannot bound the *total* server-side connections across replicas, and that is the number Postgres limits |

- **Transaction mode is the default.** Application code does not use session-mode features: advisory locks, `SET LOCAL`, cross-statement `LISTEN/NOTIFY`, and server-side prepared statements without compatibility flags.
- `pgx` sets `DefaultQueryExecMode = QueryExecModeDescribeExec` in `libs/go/dbmw`. This describes a statement without a server-side prepared statement, so a transaction-mode pooler is safe.
- PgBouncer sizes the per-service connection limits, not `pgx`. The app-side pool is small per replica, and PgBouncer multiplexes it onto a smaller server-side pool.

**A session-mode `Pooler` is deferred.**

| Field | Value |
| --- | --- |
| **Trigger** | a service needs `LISTEN/NOTIFY` across statements, an advisory lock, or a session-scoped `SET` |
| **Seam** | ✓ `Pooler` is a CRD, and a service reaches its pooler by hostname. A second pooler in session mode is a manifest plus one changed connection string. Application code does not change |
| **Cost if adopted late** | the service that needed it has already worked around the gap, usually with polling. That workaround must then be removed |

### Migrations: dbmate

Files live at `services/<service>/migrations/<YYYYMMDDHHMMSS>_<description>.sql`. Each is one SQL file with `-- migrate:up` and `-- migrate:down` sections.

**Down migrations are not used in production.** Production rollback is a forward fix: a new migration that reverses the change. Down sections are for local development.

| Environment | How they run |
| --- | --- |
| Production | `dbmate up` runs as an **init container** before the service container in the shared chart, per [ADR-0201](0201-gitops.md). The service starts only after it succeeds. An advisory lock prevents concurrent runs across replicas |
| Local | the same binary against the local database, through `mise run db:migrate` |

Engineers run the init container image locally. No separate migration image exists to drift.

**sqruff** lints SQL, both queries and migrations, at pre-commit and in CI. It is a single Rust binary, compatible with sqlfluff, and it reads `.sqlfluff` with `dialect = postgres`. It needs no Python toolchain, per [ADR-0100](0100-language-and-runtime.md).

### The OpenFGA schema is a seed Job

It is not SQL, but it is the same class of problem: a declarative schema that must be applied before consumers rely on it.

An idempotent Job in the OpenFGA chart runs in a sync wave after the Deployment is Ready. Argo CD syncs it. It writes the canonical schema and touches the **static** ops-policy grants. Both operations are idempotent, so the Job is safe on every sync. Local and deployed environments share one seeding path.

Per-human operator membership is **not** in this Job. It is runtime state, promoted and demoted in the admin console, per [ADR-0304](0304-identity-and-authorization.md).

### Zero-downtime schema changes: expand, migrate, contract

1. **Expand.** Add columns or tables, nullable or with a default. Deploy.
2. **Migrate data.** Backfills run as **Temporal workflows**, not SQL scripts, per [ADR-0302](0302-temporal.md). So they are observable, resumable, and rate-limitable. Deploy if application code needs new behaviour.
3. **Contract.** Drop old columns or tables only when no code references them.

| Hard rule | Reason |
| --- | --- |
| No destructive migration in the same deploy as the code that uses the new schema | At least one deploy boundary separates expand from the code switch |
| No long-lock `ALTER TABLE` without `lock_timeout` and a documented online-DDL plan | A long lock is an outage, and review blocks it |
| No `DROP COLUMN` until code without a reference to the column has shipped for one full production deploy cycle | The rollback target must still work |

### Multi-tenancy is row-level

Every multi-tenant table has an `org_id` column. Service code filters by the value from the request context. **Row-Level Security** is enabled on those tables, keyed on `CURRENT_SETTING('app.org_id')`. The `BeforeAcquire` hook of `pgx` sets it per request.

RLS is enabled per service when that service first becomes multi-tenant. It is not on every table by default.

| Field | Value |
| --- | --- |
| **Trigger** | a service's tables start to hold rows of more than one organisation |
| **Seam** | ✓ the `org_id` column and the `app.org_id` setting are schema and connection conventions from the start. Enabling RLS is a migration that adds a policy. No data moves and no query changes |
| **Cost if adopted late** | the table already holds rows of several tenants, so the policy is enabled against live multi-tenant data. A query that was silently cross-tenant then returns nothing, not too much |

A tenant that requires physical isolation gets its own service, and possibly its own cluster.

### Extensions

| Tier | Extensions | How they arrive |
| --- | --- | --- |
| Cluster default | `pgcrypto`, `uuid-ossp`, `pg_stat_statements` | pre-allowed in the cluster manifest. They are common enough to be cheap |
| Sanctioned per service | PostGIS, TimescaleDB, pgvector | the first service that needs one installs it in a migration and records it in its README. The extension then joins the cluster's pre-allow list |
| Anything else | any other extension | requires an ADR |

### Credentials and backups

Each service has a dedicated Postgres role with access only to its own database. Roles, grants, and passwords live in a SOPS-encrypted file, per [ADR-0202](0202-secrets.md). The operator turns it into Secrets that the chart mounts. `.env.example` holds the committed local connection string, with non-secret defaults.

[ADR-0207](0207-cluster-storage.md) owns backups. CNPG writes to the off-cluster bucket with WAL-based PITR, and the restore is rehearsed every quarter. No service has an exception.

### Major-version upgrades

A new `Cluster` is created at the new version, and CNPG replicates from the old one. Traffic then cuts over, with a short read-only window per service. This happens once per Postgres release cycle, in a planned maintenance window, per [`docs/guide/postgres-major-upgrade.md`](../guide/postgres-major-upgrade.md).

## Consequences

### Positive

- One engine and one mental model.
- Service ownership is structural: a service cannot read another service's data, even if it tries.
- Migrations live with the code they describe, so one diff carries behaviour and schema together.
- Local matches production: the same binary, the same SQL, and the same init-container shape.
- Backfills as workflows make a zero-downtime schema change a normal review item, not an event.

### Negative and Risks

- **Transaction mode rules out a narrow set of Postgres features.** Lint and the session-mode seam reduce this.
- **In a shared physical cluster, a noisy neighbour affects every service.** CNPG resource isolation, per-role slow-query alerts, and per-service connection limits reduce this.
- **Engineers from Django, Rails, or Spring expect an ORM.** They pay this cost once, during onboarding.
- **A forward fix as the only rollback path requires discipline.** [`docs/guide/database-migrations.md`](../guide/database-migrations.md) documents it.
- **RLS is opt-in per service.** A service that becomes multi-tenant without it has tenant isolation only in application code. The `org_id` column is the visible marker that a reviewer checks.

## Rules

- Every service uses Postgres. Another engine requires its own ADR.
- Each service owns exactly one logical database, with credentials scoped to it. Cross-database queries are not used.
- Cross-service data access is HTTP through the generated OpenAPI client. `(CI: ci:lint)`
- CloudNativePG operates the cluster, and pooling goes through a transaction-mode `Pooler`.
- Application code is safe for transaction mode: no advisory locks, no `SET LOCAL`, no cross-statement `LISTEN/NOTIFY`, and no server-side prepared statements without compatibility flags. `(CI: lint:sql)`
- SQL access is sqlc plus pgx. ORMs are not used. `(CI: ci:lint)`
- Migration files live at `services/<service>/migrations/`, and dbmate manages them. `(CI: lint:service-contract)`
- Migrations run as the service's init container in production, and the same binary runs locally.
- Down migrations are local-only. Production rollback is a forward fix.
- Schema changes follow expand, then migrate as a Temporal workflow, then contract. At least one production deploy boundary separates expand from the code switch.
- A multi-tenant service's tenant tables carry `org_id` and have RLS enabled, keyed on `app.org_id`.
- Sanctioned extensions are PostGIS, TimescaleDB, and pgvector, plus the cluster default set. Others require an ADR.
- Database credentials reach pods through the sops-operator from encrypted files.
